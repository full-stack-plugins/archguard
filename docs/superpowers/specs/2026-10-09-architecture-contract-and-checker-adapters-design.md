# ArchGuard：架构契约、检查器适配与核心独立性

状态：书面设计待审阅；方向已确认，尚未进入实施计划。2026-10-09，源码核对基线 `001d40c4243a920c49834da4139f51f79845eeff`。本轮只新增文档，不改产品代码、依赖、目标项目或既有任务勾选，不推送。

## 1. 产品目标与范围

ArchGuard 在项目架构阶段帮助团队明确语言、框架、MVC/DDD 等模式、模块职责、目录与命名、允许和禁止的依赖，随后持续检查实现是否符合这份架构契约。它不把“采用DDD”自动解释成领域设计正确，也不把静态依赖检查当成业务语义证明。

采用已认可的“架构契约 + 按项目选择成熟检查器”方向，沿用 CodeGuard 的适配思路，但不改动、复制替换或裁剪原 CodeGuard。第一条交付仅为 Java ArchUnit 的真实端到端流程；TSArch、Rust 分后续独立切片。各语言工具有独立维护者、接口和能力，不称为统一官方插件。

## 3. 结构选择

选择“独立核心 + 成熟工具适配 + 可选候选/追溯集成包”。只给现有 path 依赖加 optional 不能保证发行独立；立即重写全部分析器则会丢失成熟能力，均不采用。

```text
目标项目的架构契约、固定工具配置、源码目录
                    ↓
ArchGuard 核心：契约校验 → 能力匹配 → 工具适配 → 结果与覆盖
                    ↑
可选集成包：Git候选字节提取、SpecGuard追溯 → 已验证来源绑定
```

核心默认依赖图不得包含 GitGuard 或 SpecGuard；基础源码扫描不导入其类型、不发现Git仓库、不读取提交或审批。纯架构基线生命周期留在核心，当前 `domain/baseline.rs` 混入的SG/GG追溯迁到集成包。核心继续使用 GuardEngine 的中立规则/契约/证据能力，不把MVC、DDD或工具策略塞入引擎。

可选包负责校验真实候选对象、从对象读取不可变文件并核对内容清单，再调用核心；返回报告关联已验证的完整候选上下文。字符串OID、来源标签或自行序列化的快照都不能取得“已验证候选”地位。普通目录结果明确为目录快照，不冒充Git候选证据。现有五守卫调用者在迁移时显式接入此包；旧绑定和错误拒绝语义必须保留。

**发行验收是独立条件：**在不包含GG/SG或任何仓库外 sibling 路径的干净目录构建核心，并从实际分发物复建、运行无 `.git` 源码扫描；依赖图、manifest及打包清单不能残留外部 `../guard*` 路径。GE也不能例外：优先消费精确发行版本；若GE尚未可发行，只能明确交付包含固定GE源码及许可的自包含构建包，不能宣称独立crate发布完成。两种分发方式均不得联网追随main；具体发行前置状态须在实施计划核实，不在本轮发布GE。

## 4. 架构契约与工具边界

目标契约以版本化项目文件保存；以下为字段设计，不是已发布schema或新CLI：

- 项目：语言、框架及版本、选择的架构模式；模式是显式模板选择，不依赖猜测。
- 模块：名称、职责描述、源码根/包选择器、目录和命名约束。
- 规则：稳定ruleId、作用域、允许/禁止依赖、分层、环及框架使用约束。
- 执行：适配器与精确版本、构建/测试入口、覆盖范围、显式排除项。
- 例外：经确认的存量违规引用、原因、责任人及适用范围；不是全局关闭规则。

适配器声明每种规则的“支持、部分支持、不支持”。目录/命名检查可由核心读取文件清单；Java字节码依赖交由ArchUnit；框架注解/包约束仅在对应profile有验证时启用。职责文本和DDD语义中无法静态判定的部分标注需要评审，不伪装成自动规则。

报告保留ruleId、模块/文件或类/依赖位置、工具版本、实际覆盖、原始诊断及来源摘要。选中的必查规则全部被执行且满足，才是通过；真实违规是失败；缺少工具、构建失败、导入为空、无法解析报告或不支持必需语义是未验证，必须非成功退出。新适配流程拟采用0通过、2规则违规、4未验证/执行错误；若并存违规与缺覆盖，保留全部发现，总体退出4，不把不完整检查包装成已完成违规检查。现有CLI的既有退出和报告语义不悄悄修改。

## 5. 项目接入与baseline

初始化必须由用户显式触发：先展示将增加或修改的架构契约、构建依赖、测试入口与版本配置，再执行批准的修改。扫描不会偷偷安装工具、下载新版本、改写pom/源码或生成baseline。运行目标项目构建也必须是用户明确选择的测试入口；失败原样说明。

版本固定落在目标项目：ArchUnit/JUnit的精确依赖与插件版本、Maven Wrapper发行版本和校验值、JDK配置、架构测试源码及运行说明均入项目版本控制。不使用动态版本范围、latest或远程main。本轮不安装工具；实施时先对选定组合做实际兼容验证再冻结，不能把设计候选版本写成已验证。

存量违规先列出，只有用户确认的具体违规才能建立baseline。基线关联具体ruleId、位置及契约/工具配置摘要，相关内容变化须重审，不自动继承豁免。新增违规仍失败；规则变弱或扩大例外需明确确认，不自动学习失败、自动刷新快照或忽略缺覆盖。现有ArchitectureBaseline的不可变修订机制继续保留，但与“允许忽略某条违规”不能混为一件事。

## 6. 第一条 Java 端到端验收

以仓库中新增的真实、可编译 `order-service` 演示项目为首个目标，不要求外部用户仓库或Git元数据。采用Java 17、Maven Wrapper、JUnit 5和ArchUnit；具体兼容版本在实施计划及目标项目配置固定，当前尚未安装或验证。ArchUnit官方入门当前示例为1.5.1，仅作为待验证候选。

项目契约定义 `web`（入口）、`application`（用例）、`domain`（业务模型）、`infrastructure`（外部实现）。采用显式允许边：web→application，application→domain，infrastructure→domain；domain不得依赖其余三层或Spring等框架包。模式称为DDD分层示例，不宣称验证完整DDD语义。首条强制规则 `ARCH-JAVA-001` 禁止web直接依赖infrastructure。

拟在目标项目保存 `src/test/java/.../ArchitectureRulesTest.java`，入口为 `./mvnw -B -Dtest=ArchitectureRulesTest test`；这些是待实现的项目文件与命令，不是当前已有命令。

验收必须留下同一工具版本和同一规则下的实际输入、命令、输出：

1. 从不含 `.git` 的项目副本运行明确记录的Maven架构测试入口，确认编译成功、发现并执行非零架构测试、预期类被导入，正常项目通过。
2. 只修改 `OrderController`，直接引用 `infrastructure.JdbcOrderRepository`，保持Java可编译。ArchUnit测试真实失败；AG输出 `ARCH-JAVA-001`、依赖两端和可用位置，退出2。不能用编译失败代替越层违规。
3. 移除该越层边、恢复经application调用，规则和baseline不变，重新编译/运行后通过。
4. 分别验证工具缺失、编译失败、必需类未导入/空测试及声明不支持规则：输出未验证与原因，退出4，不复用上一次成功结果。
5. 验证独立核心分发物不需要GG/SG sibling；原Cargo、Java、TS分析及架构baseline受影响回归保持；CodeGuard仓库无改动。可选候选集成另验证真实字节一致性与伪造OID拒绝，不成为正常项目通过的前置条件。

这是验收标准，不是执行步骤清单；没有本轮功能测试或OpenSpec通过声明。
