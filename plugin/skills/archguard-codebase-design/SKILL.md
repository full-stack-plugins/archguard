# 模块设计评审

改编自 Matt Pocock codebase-design；原始来源、DEEPENING 与 DESIGN-IT-TWICE 参考资料保存在 `org.partme.guard/sources/`，其中宿主专用指令仅作来源材料。

先读 [公共协议](references/guard-workflow.md)。项目领域术语优先，不强制把服务、API、组件或限界上下文统称为 module。

1. 先读取统一项目模型与目标模块邻域、需求增量的 change impact，再查看实际调用方和测试，列出接口暴露的状态、顺序、错误及配置负担；声明图不能代替实际调用证据。
2. 检查接口是否隐藏复杂实现，以及不变量、错误语义、性能约束是否有清晰归属。不用接口行数/实现行数比值判断优劣。
3. 检查职责是否被迫横跨多个模块、重复对象传递或薄包装；也识别已有良好封装，避免为了“更深”盲目合并。
4. 对真实存在的变化点提出两种可比较设计，比较调用方改动、测试、兼容性、迁移成本；不为假想的第二实现增加抽象。
5. 输出建议及源码依据、反例、风险和信心程度。把建议送交架构决策，不自行提升为 enforce。
6. 对已确认且可表达的依赖边界，使用现有五种契约断言，并通过 architecture-check 执行；类型/方法语义明确标记未覆盖。

交付：问题证据、候选方案、选择依据及测试切入点。该评审不生成 ALLOW。

Java/Maven 源码治理使用公共协议中的 java 策略和 java_type 映射；复用项目基线及需求增量，以 java_analysis 的源证据检查包、层和归属。修复后重新 check/verify，不把构建子报告 ALLOW 或模型声明当作完整 Java 语义证明。
